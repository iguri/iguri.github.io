```text
相册                      → 命中 3 条  413a754
做相册                    → 命中 3 条  413a754
怎么做相册                → 命中 0 条  -
页面怎么做相册            → 命中 0 条  -
Hugo 怎么做一个相册页面   → 命中 0 条  -
```

站里明明有一篇《给 hugo 添加相册页面》，查询词一个字没漏，偏偏差不到。

这不是索引没建好，是 PaperMod 那套 `fuse.basic.min.js` 把整条查询当成**一个连续模式**去算相似度，查询越长，需要连续对上的字符就越多。

我先把现状量了一遍：78 条 `index.json`、正文 118262 字，Fuse 建索引 3.9 ms，单次查询中位 51.4 ms、最慢 93.5 ms。

十二个「站里确实有答案」的查询，它命中 4 个；八个「站里根本没写过」的查询，它硬答了 1 个。

换成自己写的 BM25 之后，同样的二十条查询，命中 10 个，硬答 0 个。连跑四百次，单次查询中位 0.20 ms、最慢 0.56 ms。

下面是换的全过程，包括两个我至今没修好的口子。

## 调低阈值更糟，调高就变成什么都敢答

先排除「阈值设太大」。站里 `config.toml` 的 `fuseOpts` 是 `threshold = 0.35`、`ignoreLocation = true`、`minMatchCharLength = 1`，我原样复制进脚本，然后往两头各扫一遍：

| threshold | 正样本命中（12 条） | 负样本硬答（8 条） |
|---|---|---|
| 0.1 | 3 | 0 |
| 0.2 | 3 | 0 |
| 0.35（站点现值） | 4 | 1 |
| 0.45 | 9 | 1 |
| 0.55 | 10 | 2 |
| 0.65 | 10 | 3 |
| 0.75 | 10 | 7 |
| 0.85 | 11 | 8 |

两头都不通。往松调（0.1、0.2）命中数掉到 3，往紧调命中是上去了，但紧到 0.85 时八个负样本全被硬答——它等于谁问都给答案。

这个表的形状说明问题不在阈值：单靠一个编辑距离分数，召回和精度就是同一条线上的两端，调不动曲线本身。

根子在分词。中文没有空格，Fuse 拿到的是 `Hugo 怎么做一个相册页面` 一整串，而人提问必然带「怎么」「做一个」「页面」这些功能词，它们在整串相似度里把「相册」这个真信号稀释掉了。

## 中文得先切出「词」，才谈得上 IDF

BM25 要词频和文档频率，前提是先有词。我不上分词词典，按二元组切，英文和标识符按整词切：

```js
function tokenize(text) {
  const lower = text.toLowerCase();
  const grams = [];
  for (const seg of lower.match(/[\u4e00-\u9fa5]+/g) || []) {
    if (seg.length === 1) grams.push(seg);
    for (let i = 0; i < seg.length - 1; i++) grams.push(seg.slice(i, i + 2));
  }
  return [...grams, ...(lower.match(/[a-z0-9_.#+-]{2,}/g) || [])];
}

tokenize('Hugo 怎么做一个相册页面');
// ["怎么","么做","做一","一个","个相","相册","册页","页面","hugo"]
```

「个相」「册页」是噪音，但「相册」被切出来了，这就够：噪音的 idf 低（它们散落在很多文档里），后面算分时自然压不下去也抬不起来。

反过来验一次：只留英文词表、中文二元组全砍，十二条正样本查询里有 4 条得分直接归零——`懒加载`、`首行缩进`、`相册`、`注册跳转到 wp-login 怎么办` 全部查不到。别指望英文分词规则顺手处理中文。

## 块切多大：200 字时命中了也读不到答案

检索单元不能是整篇文章。我按 `##` 分段，再把段落打包成不超过 800 字的块，块间不重叠。

块上限直接决定召回质量，我拿七条带「gold 原文串」的查询扫了一遍：

| 块上限 | 片段数 | Top1 指向对的文章 | 答案串真在块内 | 首块平均字数 |
|---|---|---|---|---|
| 200 | 732 | 7/7 | 2/7 | 167 |
| 400 | 391 | 7/7 | 3/7 | 360 |
| 800 | 241 | 7/7 | 5/7 | 612 |
| 1600 | 178 | 7/7 | 6/7 | 750 |

看第三列和第四列的差距。块越小，Top1 越容易指向对的那篇，但**答案经常被切到隔壁块**——200 字一块时七条里只有两条，命中的块里真能读到答案。

Top1 对了而块里没答案，交给下游模型就是让它拿半截话编，比查不到更糟。

800 是这条曲线的拐点：再翻到 1600，答案命中只多一条，单块字数却涨到 750，喂给模型的上下文白涨 23%。

## 空行会把代码块劈成两半

这是第一个真 bug，也是最容易被略过的。

我一开始就是按空行切段：`sec.split(/\n{2,}/)`。贴代码的人习惯在函数之间留空行，于是**代码围栏被空行劈成了两截**。

统计下来，朴素按空行切出 1383 个段落，其中 155 个含围栏，而这 155 个里有 **44 个**的 ` ``` ` 数量是奇数。落到块级别，那版 248 个块里有 18 个围栏不配对。

修法是切段时跟踪围栏状态，围栏内的空行不算段落边界：

```js
function blocks(text) {
  const out = [];
  let buf = [], inFence = false;
  for (const line of text.split('\n')) {
    if (line.trimStart().startsWith('```')) inFence = !inFence;
    buf.push(line);
    if (!inFence && line.trim() === '') { out.push(buf.join('\n')); buf = []; }
  }
  if (buf.length) out.push(buf.join('\n'));
  return out.map(s => s.trim()).filter(Boolean);
}
```

改完，133 个含围栏的段落里围栏不配对的是 0 个，241 个块里也是 0 个。块数从 248 降到 241，平均字数 522 涨到 538——代价很小，但换来的是那 18 个块不再是死块。

超长段落还得单独兜一层：切点算在 800，如果这个位置落在未闭合的围栏里，就把切点后移到围栏收尾，宁可这一块超长：

```js
if (end < text.length && fences % 2 === 1) {
  const close = text.indexOf('```', end);
  if (close !== -1) end = close + 3;   // 保围栏完整，块超长也认
}
```

现在 241 个块里 23 个超过 800 字，分布是中位 534、p90 正好 800、最长 3254。我没有再往下压，因为长块都是代码——代码本来就是整段的语义单元。

顺带把块尾形态数了一遍：207 块收在句末标点或代码围栏上，16 块收在加粗小标题、表格行这类 markdown 结构上，18 块（7.5%）确实断在半句里。这 7.5% 是我接受的下限，再往上抠成本不划算。

## 第二个 bug：一个 0 字的片段拿了最高分

第一版跑完，`Hugo 怎么做一个相册页面` 分数 23.74，是全部候选里最高的，但覆盖率算出来是 **0**，被闸门拦掉，等于白查。

我以为是分词问题，把片段打出来才发现：

```js
const r = db.prepare('select id,slug,length(text) L from chunks where slug=? limit 3').all('413a754');
// [ { id: 31, slug: '413a754', L: 0 }, { id: 32, L: 595 }, ... ]
```

31 号片段正文 0 个字。原因是 `body.split(/\n(?=## )/)` 切出来的第一段是「空行 + 标题」，我把这个空串也当段落入队了。空片段照样进倒排、照样能被匹配到分数（分数全由 heading 里的词贡献），只是正文一个字没有。

一行 `if (!para.trim()) continue;` 修掉。这类 bug 最难发现的地方是它不报错：分数算得比谁都高，只有覆盖率那一列会露出 0。

还有一次是 `TypeError: postings[x].push is not a function`。语料里有个 token 叫 `constructor`（来自一篇贴 LangChain 消息结构的代码块），用普通 `{}` 装倒排表时，`postings['constructor']` 命中的是 `Object.prototype.constructor`，拿到的是函数不是数组。换 `Map` 或者 `Object.create(null)` 都行。

## 分数高不等于该回答，覆盖率才是那道闸门

这是整套东西里唯一值钱的部分。只按 BM25 分数排序、不设门，二十条查询全都会给出答案，包括站里压根没写过的八条。

只加一道分数阈值也不够。`iPhone 换电池多少钱` 拿到 9.35 分，答成了《给 WordPress 博客系统评论框显示用户 UA》——那篇文章正文里 `Safari`、`Android`、`Edge` 一串英文词，跟「iPhone」沾了个边。

所以第二道门是 **IDF 加权覆盖率**：把查询词按 idf 加权，看得分最高的那个块到底覆盖了多少。

```js
const hay = new Set(tokenize(text + ' ' + heading));
let hit = 0, all = 0;
for (const t of terms) { const w = idf(t); all += w; if (hay.has(t)) hit += w; }
const cover = all ? hit / all : 0;

if (bestScore < 8) return { verdict: 'LOW_SCORE', cover };
if (cover < 0.35) return { verdict: 'LOW_COVER', cover };
return { verdict: 'OK', text };
```

用 idf 加权而不是数词个数，是因为「怎么」「一个」这类词满库都是、idf 接近 0，不该因为命中就给分。真正该问的是：「iPhone」「电池」这些稀有词，你块里有吗——没有就别答。

两道门一起扫（同二十条查询）：

| 门限 | 答对 | 硬答 | 漏答 |
|---|---|---|---|
| 无门 | 12/12 | 8/8 | 0 |
| 分数 ≥ 8 | 11/12 | 2/8 | 1 |
| 覆盖率 ≥ 0.35 | 11/12 | 0/8 | 1 |
| 分数 ≥ 8 且覆盖率 ≥ 0.35 | 10/12 | 0/8 | 2 |
| 分数 ≥ 12 且覆盖率 ≥ 0.4 | 8/12 | 0/8 | 4 |

注意「覆盖率 ≥ 0.35」单独一道就已经把硬答压到 0，代价只漏 1 条；而分数阈值单独用时还放过 2 条硬答。**卡不卡得住，主要靠覆盖率。**

两道门都留着是因为它们筛的东西不同：分数挡「词都命中但全是常见词」的块，覆盖率挡「分数够高但只命中一两个词」的块。

## 两个我还没修好的洞

**短查询被自己的分数下限拦住。** 单问「相册」，覆盖率 1.0，但 score 只有 7.57，被 `>= 8` 挡掉。二元组切开后「相册」只有一个词项，没有别的词帮它抬分，绝对分数天然比长查询低。

**带口语的长查询覆盖率不够。** 「多个 agent 同时提交代码冲突」在《8 个 agent 抢一个工作副本》那篇上拿到 11.52 分，覆盖率却只有 0.23——原文写的是 `index.lock`、工作副本、并发写，「提交」「冲突」这些字眼没出现在那一段。它被 LOW_COVER 误拒。

把门限放松到 `score >= 4 && cover >= 0.2`，这两条都能救回来，二十条查询满分。但那是拿同一套二十条查询调出来的参数，换成没见过的问法必然翻车。我没敢这么定，先按 8 / 0.35 留着，把它记成已知误拒。

## FTS5 两个分词器我都试过，都不行

`node:sqlite` 自带 FTS5，我第一反应是把切块塞进去，省掉自己维护倒排。用 `tokenize='unicode61'` 试下来：

```js
'相册' → 1 条   '首行缩进' → 0 条   '缩进' → 0 条   '页面' → 0 条
// fts5vocab 打出的真实 token: [ '实现首行缩进效果', '相册', '这个相册页面很好' ]
```

它把一整串没断开的连续中文当成**一个 token**，所以两字的「相册」能中（因为它自己成了独立 token），四字的「首行缩进」永远中不了。

换 `tokenize='trigram'` 更坑，按字符三元组切，两字词直接判死：

```js
'相册' → 0 条   '缩进' → 0 条   '图床' → 0 条   '过期' → 0 条
'首行缩进' → 1 条   'grid-template-columns' → 4 条
```

两字中文词是站内搜索的主力，trigram 把它们全废了。要救只能在查询侧对两字词退化成 `instr(body, ?) > 0` 的表扫，那还不如自己维护倒排——反正 241 个块建库 0.2 秒。

## 眼下的代价

索引落盘 574 KB，gzip 后 171 KB。站点现在那份 `index.json` 是 297 KB / gzip 120 KB。

**为了能答对，首屏要多下 51 KB。** 这是我目前唯一没解决的代价，也是我唯一不敢说「换就完了」的原因。

这套思路和之前[给评论区接 AI 管家]({{< relref "blog/dsh-ai-comment-agent/index.md" >}})时用的粗筛是一回事——那里也是中文 2-gram、也是站里没写过就直说不知道，只是那时语料小，没做覆盖率这道门。

下次要试的是把覆盖率门限从 0.35 降到 0.25，同时把 `相册` 这类单词语查询的分数下限单独调成 6——先看能不能在不动误召回的前提下把漏答收回来。
